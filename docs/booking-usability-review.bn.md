# বুকিং ও প্রশাসনিক পাতার যাচাই

তারিখ: ৯ অক্টোবর ২০২৬

## সংশোধন

- বুকিং ফরমের state এখন আগের state থেকে আপডেট হয়। একসঙ্গে কয়েকটি ঘর বা browser autofill বদলালে অন্য ঘরের নির্বাচন হারানোর ঝুঁকি কমানো হয়েছে।
- সংগ্রহের পদ্ধতি সত্যিই বদলালেই সংগ্রহের এলাকা খালি হয়। একই পদ্ধতি আবার autofill হলে এলাকা মুছে যায় না।
- প্রতিটি ঘরের আলাদা id, name ও label রয়েছে। প্রেরক এবং প্রাপকের autofill section আলাদা; এলাকার select-এ autofill বন্ধ।
- বুকিংয়ের server error অনুযায়ী অনুমোদন, মূল্য পরিবর্তন, এলাকা, হাব ও সেবার সমস্যা বাংলায় বা ইংরেজিতে দেখানো হয়। অজানা server error-এর অভ্যন্তরীণ তথ্য প্রকাশ করা হয় না।
- COD অনুমোদন না থাকলে ব্যবসায়িক অ্যাকাউন্টের লিংক দেখায়। অনুমোদনের নিয়ম শিথিল করা হয়নি; COD মানও স্বয়ংক্রিয়ভাবে বদলানো হয় না।
- মূল্য বদলালে নতুন quote নেওয়া যায়, এবং আবার সম্মতি দিতে হয়। লেখা নাম–ঠিকানা রাখা হয়।
- Team মেনু লিংক নির্বাচন, একই পাতার লিংক নির্বাচন, বাইরের ক্লিক, Escape এবং locale/route পরিবর্তনে বন্ধ হয়। মোবাইল staff লিংকের query-only navigation-ও পরীক্ষা করা হয়েছে।
- অনুমোদিত তিনটি হাবের নাম, অবস্থান ও পূর্ণ ঠিকানা ইংরেজি পাতায় ইংরেজি এবং বাংলা পাতায় বাংলা হয়। শাখায় জমার quote-তেও ঠিকানার একই অনুবাদ ব্যবহৃত হয়। ডেটাবেসের হাব id/ঠিকানা বদলানো হয়নি; অজানা কাস্টম ঠিকানা অপরিবর্তিত থাকে।
- ব্যবসা ও কর্মীর আবেদন কোথায় জমা হয়, ফরমেই স্পষ্ট করা হয়েছে।

## Submit for review কোথায় যায়

ব্যবসার ফরম PUT /operations/business এবং কর্মীর ফরম POST /operations/applications-এ সংরক্ষিত হয়। Dropzo-এর ADMIN ভূমিকার প্রশাসকেরা Admin → Operations পাতায় অপেক্ষমাণ আবেদন দেখে অনুমোদন বা প্রত্যাখ্যান করেন। এটি ইমেইল পাঠানো, bKash/Stripe-এ পাঠানো কিংবা স্বয়ংক্রিয় অর্থ হস্তান্তরের ব্যবস্থা নয়।

শুধু পড়ার ডেটাবেস যাচাইয়ে ১টি অননুমোদিত ব্যবসায়িক অ্যাকাউন্ট এবং ১টি PENDING কর্মীর আবেদন পাওয়া গেছে। কাউকে অনুমোদন দেওয়া হয়নি।

## ছবির বুকিং ব্যর্থতার ব্যাখ্যা

ছবিতে ব্যবসায়ীর পাওনা BDT 0.06; অর্থাৎ পণ্যের টাকা সংগ্রহের পরিমাণ শূন্য নয়। সার্ভারের shipment.service.ts-এ codAmount > 0 হলে অনুমোদিত business account বাধ্যতামূলক। তা না হলে HTTP 409, “Approved business account required for COD” ফেরত আসে।

ছবির ব্যর্থ অনুরোধের network response বা লগ পাওয়া যায়নি। ফলে ওই একটি বুকিংয়ের একমাত্র কারণ অনুমোদনই ছিল—এমন নিশ্চিত দাবি করা হচ্ছে না। নতুন UI এখন নির্দিষ্ট অনুমোদন ত্রুটি এবং অন্য পরিচিত server error আলাদা করে দেখায়।

## হার্ডকোড বনাম ডেটাবেস

AdminOverview → /admin/dashboard-stats → backend admin.service.ts → Prisma count/aggregate থেকে সংখ্যাগুলো আসে। শুধু পড়ার ডেটাবেস পরীক্ষার সময়:

| বিষয় | সংখ্যা |
| --- | --- |
| ডিলিট না হওয়া CUSTOMER ব্যবহারকারী | ৪ |
| ডিলিট না হওয়া COURIER ব্যবহারকারী | ৭ |
| ডিলিট না হওয়া পার্সেল | ২২ |
| ডিলিট না হওয়া PAID payment-এর যোগফল | ১,৮০০ টাকা |

ছবির সংখ্যা এই যোগফলের সঙ্গে মিলে। এটি হার্ডকোড নয়, তবে বাস্তব ব্যবসায়িক কার্যক্রমের বিশুদ্ধ হিসাবও নয়: ডেটাবেসে পরীক্ষামূলক ব্যবহারকারী, কর্মী, হাব ও CHECKOUT fixture রয়েছে। PAID যোগফলে অন্তত একটি CHECKOUT fixture-এর ১২০ টাকার Stripe payment আছে। COD পণ্যের পাওনা এই revenue aggregate-এর অংশ নয়।

টেস্ট রেকর্ড মুছে ফেলা, অর্থ পাঠানো, ব্যবহারকারীর ক্ষমতা বদলানো বা live parcel তৈরি করা হয়নি। Hub Management-এর Add/Edit/Delete বোতামগুলোর UI action এখনও যুক্ত নেই; এটি ভাষা সংশোধনের বাইরে একটি আলাদা বিদ্যমান সীমাবদ্ধতা।

## যাচাই

Production build ও TypeScript সফল। Lint-এ error নেই; আগের sidebar document.cookie সতর্কতাটি আছে। পূর্ণ regression run-এ আগের ৭৩টি পরীক্ষা পাস করেছে। নতুন usability ফাইলের চূড়ান্ত পৃথক run-এ ১১টির ১১টি পরীক্ষা পাস করেছে; মোট ৮৪টি পরীক্ষা সফলভাবে যাচাই হয়েছে। প্রাথমিক নতুন পরীক্ষার selector সমস্যা সংশোধন করে পুনঃপরীক্ষা করা হয়েছে। পরীক্ষাগুলো API mock ব্যবহার করে; বাস্তব পার্সেল, আবেদন বা payment তৈরি করে না।

প্রাথমিক যাচাইয়ের সময় সংশোধনগুলো স্থানীয় ছিল। প্রকাশের চূড়ান্ত অবস্থা সংশ্লিষ্ট GitHub commit ও deployment-এর মাধ্যমে যাচাই করতে হবে।
